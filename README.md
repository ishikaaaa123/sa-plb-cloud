# SA-PLB: Staleness-Aware Predictive Load Balancing under Delayed Monitoring

SA-PLB is a research prototype that studies whether a load balancer can make safer routing decisions when monitoring information may be delayed.

The system uses a machine-learning (ML) model to estimate the response time of each replica. Before trusting those predictions, SA-PLB checks how old the monitoring observations are:

-   **Fresh monitoring data:** use the ML prediction and route to the
    replica with the lowest predicted response time.
-   **Stale monitoring data:** fall back to Weighted Round Robin (WRR).

The project compares four routing policies: Round Robin (RR), Weighted
Round Robin (WRR), ML-based Predictive Load Balancing (ML), and
Staleness-Aware Predictive Load Balancing (SA-PLB).

> **Important: this is a simulation.** Workload arrivals, request sizes,
> replica behaviour, queues, monitoring delays, interference, and
> response times are generated by the simulator. The reported
> performance values are simulated results, not measurements from real
> cloud containers.

## 1. Research problem and contribution

Cloud load balancers make routing decisions using information about the
state of backend replicas. In a dynamic environment, monitoring
information may arrive late. A replica that appeared lightly loaded when
it was measured may already be busy when the load balancer uses that
measurement.

A predictive load balancer can therefore make a poor decision if it
trusts old monitoring data.

The contribution of SA-PLB is an explicit **monitoring-data freshness
check** before using ML predictions. If the observations are too old,
SA-PLB uses WRR as a fallback policy instead of relying on potentially
misleading predictions.

This prototype evaluates that decision rule under different simulated
workload, interference, and monitoring-delay conditions. It does not
claim that SA-PLB is universally better than other load-balancing
policies.

## 2. Routing policies

All four policies are evaluated against the same generated request
workload within each paired scenario.

  -----------------------------------------------------------------------
  Policy                              How it chooses a replica
  ----------------------------------- -----------------------------------
  **RR --- Round Robin**              Sends requests to replicas in a
                                      repeating order.

  **WRR --- Weighted Round Robin**    Distributes requests using
                                      configured static replica weights.
                                      The implementation uses smooth
                                      weighted round robin.

  **ML --- Predictive Load            Predicts the response time for each
  Balancing**                         replica using the latest monitoring
                                      observation delivered to the
                                      balancer, then selects the replica
                                      with the lowest predicted response
                                      time. It does not apply a freshness
                                      gate.

  **SA-PLB**                          Uses the ML decision when the
                                      monitoring observations are fresh
                                      enough. If the oldest observation
                                      used for the decision exceeds the
                                      configured freshness threshold, it
                                      falls back to WRR.
  -----------------------------------------------------------------------

### SA-PLB decision rule

For each routing decision, the simulator calculates the age of the
monitoring observations used:

`observation_age = decision_time - collected_at`

It then considers the maximum age among the candidate observations:

-   If `maximum_observation_age <= freshness_threshold`, use ML.
-   If `maximum_observation_age > freshness_threshold`, use WRR.

The threshold is measured in seconds. In the corrected experiment
included in `results_corrected`, the selected threshold is **4.0
seconds**.

## 3. Simulation design

### Request workload and queues

-   A public Zenodo trace named `dataset-replica-mcr-mt.csv` is used to
    derive a relative workload-intensity pattern only.
-   The implementation counts records in one-minute `timestamp_2`
    buckets, applies square-root compression, and selects the most
    bursty 20-minute window.
-   These record counts are a workload proxy. They are **not**
    interpreted as actual incoming request counts or measured request
    arrival rates.
-   Individual request arrivals are generated synthetically using a
    non-homogeneous Poisson process guided by the relative pattern.
-   Request sizes and request types are generated synthetically.
-   Each replica is represented by a First-Come, First-Served (FCFS)
    queue.
-   Simulated response time is queue waiting time plus service time.

### Replica configuration

The experiment uses three simulated replicas:

  Replica     CPU cores   Relative speed    Memory
  --------- ----------- ---------------- ---------
  R0                  2              1.0   1024 MB
  R1                  2              0.9   1024 MB
  R2                  1              1.1    512 MB

The WRR weights used in the experiment are 4, 4, and 2 for R0, R1, and
R2 respectively.

### Monitoring and delayed information

-   Replicas are monitored approximately every 0.5 seconds, with
    sampling-time jitter.
-   A sample records the replica state at `collected_at`.
-   The sample becomes available to the load balancer at `available_at`.
-   Delivery delay is simulated; occasional additional monitoring stalls
    are also included.
-   A routing policy can only use monitoring samples that have already
    been delivered.

This separation between collection time and availability time makes it
possible to simulate stale monitoring information.

### Interference

The simulator can introduce hidden slowdown episodes for individual
replicas. An episode lasts approximately 20--60 seconds and multiplies
service time by a factor between 2.0 and 3.5.

The corrected experiment tests interference rates of:

-   0.00 episodes per replica per minute
-   0.10 episodes per replica per minute
-   0.25 episodes per replica per minute

These are simulator settings, not measured failure or interference rates
from a production cluster.

## 4. Machine-learning model

The predictive policy uses `HistGradientBoostingRegressor` from
scikit-learn.

-   **Prediction target:** log-transformed response time. Predictions
    are converted back to milliseconds for evaluation and routing.
-   **Training data:** generated by running random routing in the
    simulator, so the training log includes examples from different
    replicas and system states.
-   **Features:** observed active requests, observed queue length,
    observed CPU and memory usage, recent observed response time,
    request size, request-type cost, replica cores, replica speed, and
    estimated service time.
-   **Freshness:** observation age is deliberately excluded from the
    base ML feature list. The separate SA-PLB freshness layer is
    responsible for checking observation age.

The corrected run contains 54,749 training examples, 9,962 validation
examples, and 10,015 test examples.

The training log is split chronologically by simulation period: the
first six periods are used for training, the seventh for validation, and
the eighth for testing. The validation and test periods use separate
random seeds.

### Interpretation

-   With no simulated interference, WRR has the lowest mean response
    time in these scenarios.
-   Under the tested interference conditions, ML and SA-PLB have lower
    mean response times than RR and WRR.
-   Increasing monitoring delay generally increases the mean response
    time of the ML-based policies in these scenarios.
-   SA-PLB is close to ML in several scenarios and has a lower mean
    response time than ML in some delayed-monitoring scenarios.
-   SA-PLB does **not** outperform ML or WRR in every condition. For
    example, when interference is zero and monitoring delay is 0.10
    seconds, WRR is faster than both ML and SA-PLB.
-   The results show a trade-off: rejecting stale predictions can
    protect the routing decision from old information, but the fallback
    policy is not necessarily the fastest choice in every workload.

These results support a scenario-dependent conclusion, not a claim of
universal superiority.

  Test MAE                                                      457.02 ms

  Test RMSE                                                   1,191.28 ms

  Test median-predictor baseline                              1,708.96 ms
  MAE                            

  Test median-predictor baseline                              4,343.90 ms
  RMSE                           
  -----------------------------------------------------------------------

The test MAE is lower than the median-predictor baseline MAE in this
test split. However, the validation and test error values differ
substantially, so the test result should not be presented as proof of
uniformly strong prediction accuracy.

Although the validation and test periods have the same configured peak
utilization (0.80) and interference rate (0.10), their realised
response-time distributions differ:

  Metric                       Validation period   Test period
  -------------------------- ------------------- -------------
  Mean response time                   12,268 ms      1,931 ms
  Median response time                    372 ms        347 ms
  P95 response time                    84,878 ms     12,884 ms
  Requests above 30,000 ms                14.85%         0.00%

The validation period therefore contains a much heavier
high-response-time tail. The simulator uses independent random seeds and
stochastic interference schedules; these can produce different realised
conditions even when the configured rates match. The available results
establish the distribution difference, but do not by themselves prove
the exact cause of the extreme tail.

This is an important limitation. More independent validation and test
periods, with distribution comparisons and uncertainty estimates, would
make the model evaluation more robust.

## 9. Dashboard

The Streamlit dashboard provides an interactive demonstration of the
simulated system. It displays:

-   The three replica configurations.
-   The four routing policies and their performance comparison.
-   Per-replica monitoring values such as CPU, memory, active requests,
    queue length, and metric age.
-   Individual request routing decisions and ML predictions.
-   The SA-PLB decision branch and whether WRR fallback was used.

The dashboard is a demonstration interface. It uses a built-in synthetic
workload shape and should not be treated as an exact reproduction of the
Zenodo-derived full experiment or as the source of the final multi-seed
results in `results_corrected/`.

To launch it:

``` bash
python -m streamlit run app.py
```

For a demonstration of the two SA-PLB branches:

1.  Use a relatively low monitoring delay and a higher freshness
    threshold to demonstrate the ML branch (`sa_ml`).
2.  Increase monitoring delay and lower the freshness threshold to make
    stale observations more likely; inspect individual requests for the
    WRR fallback branch (`sa_wrr`).
3.  Check the displayed metric age, decision branch, and fallback flag.
    A particular request may still use ML if its observations happen to
    be fresh.

## 11. Installation and reproduction

Use Python 3.10 or newer (recommended) and create a virtual environment.

### macOS / Linux

``` bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install numpy pandas scikit-learn matplotlib streamlit
```

### Run the experiment

Place the Zenodo file `dataset-replica-mcr-mt.csv` somewhere on your
computer, then pass its actual path to the script:

``` bash
python run_all.py --zenodo /actual/path/to/dataset-replica-mcr-mt.csv --out results_new
```

Replace `/actual/path/to/dataset-replica-mcr-mt.csv` with the real
location of the file. Do not copy the placeholder path literally.

A shorter smoke run can be executed with:

``` bash
python run_all.py --zenodo /actual/path/to/dataset-replica-mcr-mt.csv --out results_quick_new --quick
```

The full experiment can take substantially longer than the quick run
because it evaluates multiple policies, interference rates, monitoring
delays, random seeds, and threshold candidates.

### Important reproduction notes

-   Pass a valid `--zenodo` path when reproducing the Zenodo-derived
    workload experiment. If the file is omitted or cannot be read, the
    workload loader can use its built-in synthetic fallback shape; that
    is a different workload input and should not be described as the
    Zenodo-derived run.
-   Use a new output directory (such as `results_new`) when running
    another experiment so that the included `results_corrected/` outputs
    are not overwritten.
-   The final policy comparison uses separate test seeds from the seeds
    used to select the SA-PLB threshold.
-   The dashboard is a demonstration interface and is not an exact
    reproduction of the full experiment.

## 12. Limitations and future work

1.  **Workload proxy:** Zenodo record counts are used only as a relative
    workload-intensity proxy, not as verified incoming request counts.
2.  **Simulation rather than deployment:** Request arrivals, service
    times, replica resources, queues, monitoring delays, interference,
    and response times are simulated.
3.  **Validation/test tail difference:** The validation and test periods
    have matching configured utilization and interference rates but
    substantially different realised response-time distributions. More
    independent periods are needed.
4.  **Limited final test seeds:** The final policy comparison uses three
    test seeds. No statistical significance test is reported.
5.  **Threshold scope:** The 4.0-second threshold is selected for this
    simulator's validation conditions; it is not a universal production
    threshold.
6.  **Fallback choice:** WRR is the only fallback policy evaluated.
7.  **Feature comparison:** Observation age is excluded from the base ML
    features. An age-aware ML baseline could be studied in future work.
8.  **Distribution shift:** The model is trained using random-routing
    data but is evaluated under policy-driven routing, which can change
    the states encountered by the model.
9.  **Dashboard separation:** The dashboard's synthetic demonstration
    workload is not the same as the Zenodo-derived workload used by the
    corrected batch experiment.

## 13. Conclusion

SA-PLB adds an explicit freshness check to predictive load balancing. It
uses ML predictions when monitoring observations are sufficiently fresh
and falls back to WRR when those observations are stale.

The corrected simulation demonstrates that monitoring delay and replica
interference can materially affect routing performance. It also shows
that SA-PLB's benefit depends on the scenario: the fallback can help
avoid stale ML decisions, but it does not guarantee the lowest response
time in every condition.

The main contribution of this project is the design and simulation-based
evaluation of a staleness-aware routing decision. Further work with more
independent runs, richer real-world traces, and deployment experiments
is required before drawing conclusions about production cloud systems.
